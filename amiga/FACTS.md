## 2. Source hardware (MAME `nespal`)
Driver: `src/mame/nintendo/nes.cpp` (fetched from mamedev/mame master; copy of the relevant parts in scratchpad only).
* `nespal`: `m_maincpu->set_clock(PAL_APU_CLOCK)` (l.452) — RP2A07 6502 core without decimal mode; `PPU_2C07(config.replace(), m_ppu)` (l.454); NMI = `INPUT_LINE_NMI` from the PPU (l.456).
* Video: `set_refresh_hz(50.0070)` (l.461), `set_size(32*8, 312)` (l.464), `set_visarea(0, 32*8-1, 0, 30*8-1)` (l.465) → 256×240 visible, 312 lines/frame, vblank `VBLANK_FIRST_SCANLINE 241 … VBLANK_LAST_SCANLINE_PAL 310` (`ppu2c0x.h` l.61, l.65).  [D]
* CPU clock **1 662 607 Hz**; measured from the MAME trace as the interval between `$4014` writes: **33 247.5 CPU cycles per frame** (min 33 236, max 33 258, 1 497 frames) = 312 × 106.5625.  [R]
* Memory map (standard NES): `$0000-$07FF` RAM (mirrored to `$1FFF`), `$2000-$2007` PPU (mirrored to `$3FFF`), `$4000-$4017` APU + OAM-DMA (`$4014`) + joypads (`$4016/$4017`), `$C000-$FFFF` PRG (16 KB mirrored at `$8000`).  Reset/NMI/IRQ vectors from ROM: RESET `$C184`, NMI `$C23B`, IRQ `$FFF0` (a stub: never enabled, `SEI` at reset). [R]
* Sound: the 2A07 internal APU: pulse ×2, triangle, noise, DMC; Excitebike uses pulse/triangle/noise plus **one direct write to `$4011`** (DMC DAC); `$4010/$4012/$4013` are never written (no DMC sample playback). [R]
* Controls: controller 1: A = accelerate, B = turbo, D-pad, Start, Select, read serially via `$4016`. Amiga mapping: see §6.

## 3. Code analysis (from ROM)
* **Code is fixed ROM** (16 KB at `$C000`); no code is ever executed from RAM: no `JMP/JSR` to `$0000-$07FF`; nothing writes into ROM space (NROM). **No self-modifying code.** [R, grep over the disassembly; to be re-proved mechanically by the control-flow tool in step 2]
* **Computed jumps:** four `JMP (zeropage)` jump tables (`ram_0000_t05_jmp … t08_jmp`, disassembly l.2155, 4729, 4919, 7395) plus RTS-trick dispatch (to be enumerated mechanically; targets are in ROM tables).  Static translation handles them with a target set discovered from the tables and a *checked* fallback for unknown targets (trap, never silent).
* **Instruction set:** official 6502 only: no illegal opcodes, no BRK, decimal mode never enabled (only one `CLD`). [R]
* **Mid-frame effects:** per frame exactly 2×`$2000`, 2×`$2005` writes: one split (HUD/playfield) timed by **sprite-0 hit** polling of `$2002`; ~380 reads of `$2002` per frame on average in the wait loop (10 362 reads of `$2002/$4016/$4017` in 3 s). So the PPU must give the sprite-0 hit at the correct *cycle*, and scroll/ctrl writes after it must take effect from the correct scanline. [R, MAME trace `ref/mame_trace.lua`]
* **PPU use per frame** (30 s trace, 1 501 frames): `$4014` OAM DMA every frame; ≈1.4 `$2007` writes/frame average (4 600 in a title-sequence burst, up to 2 176 in a level-load frame); `$2006` 4/frame. [R]
* **Video model:** tile+sprite PPU, 2 nametables (vertical mirroring), CHR-ROM (no CHR RAM), 64 sprites of 8×8 (or 8×16: to be confirmed from `$2000` bit 5), 8 per scanline, palette RAM 32 bytes (≤25 colours on screen from the 64-entry master palette). [R, partly assumed pending step 1]
* **Sound engine:** all sound is software-generated by writing APU registers from the game's own sound engine (a 6502 routine driven once per frame from NMI).  Therefore: faithful APU model (pulse/triangle/noise/DMC-DAC, frame counter, length counters, sweeps, envelopes, 2A07 noise/DMC period tables) rather than captured streams — the register-write trace is the baseline. [R/A]
* **Timing budget (estimates, to be replaced by measurements in step 1):**
  * Source: 33 247 CPU cycles/frame at 50.007 Hz.
  * Target: A1200 PAL 68EC020 @ 14.18758 MHz → 283 751 clocks/frame, **≈ 8.5 68020 clocks per 6502 cycle**.  A translated 6502 instruction (avg ≈ 3.5 cycles) costs ≈ 4–8 68020 instructions (≈ 15–30 clocks) from fast RAM, so a *fully busy* 6502 would be roughly at the limit; the game's wait loops (NMI idle loop, the `$2002` sprite-0 spin) are fused/skipped by the scheduler, so average load is expected to be well within the budget. PPU rendering and Chunky→planar conversion are the larger risk (§5).
* **Approach: (A) static translation** of the 6502 code to 68020 + hardware emulation (PPU, APU, joypads, OAM-DMA) around it.  Justification: fixed 16 KB ROM, no banking, no self-modifying code, only four computed-jump tables, official opcodes only.  (B)/(C) not needed.

## 5. Known risks / open design points
1. PPU fidelity: sprite-0 hit timing, sprite overflow, 8-per-line limit, OAM address/`$2003` behaviour, PPU register open-bus/`$2007` read buffer, the `$2002` vblank flag race at NMI time (Excitebike polls `$2002`).
2. Rendering strategy on AGA: scanline-batched chunky render (exact, handles all mid-frame changes) + c2p, vs. native planar tile blits with hardware scroll + copper split.  Decision after measuring step-1 PPU activity; goal is byte-exact picture, no colour reduction (6 bitplanes ≥ 25 simultaneous colours; the 64-colour master palette is mapped exactly, AGA 24-bit).
3. 2A07 APU in software at the highest rate Paula sustains (mixing 4 channels to 2 Paula channels, or 8-bit samples at ~28 kHz).
4. Emphasis bits (`$2001` bits 5-7) and greyscale on PAL: exact table needs to come from MAME's PPU2C07 palette code.

## 6. Assumptions and open questions
Assumptions (defaults of the porting prompt, listed per its rules):
* "PAL A1200 020 2 MB FastRAM": A1200 (68020 @ 14.19 MHz, AGA, **2 MB chip + 2 MB fast RAM** — taken as *additional* fast RAM, i.e. a stock A1200 with a 2 MB fast expansion), Kickstart 3.1, **PAL only** (the PAL game has 50 Hz timing; NTSC Amiga build only if requested).
* Joystick port 2; fire = A (accelerate), 2nd button/up+fire = B (turbo) — fire = Start on title screens (the prompt's "start = fire"); to be revisited after step 1 when menu flow is known.
* Full fidelity, tested in FS-UAE (needs Kickstart) and `qemu-m68k` for byte-exact dumps.

Blockers that cannot be derived:
1. **Kickstart 3.1 ROM for FS-UAE** (test only, never shipped) — please provide a path or upload it; until then everything except the FS-UAE steps (boot/display/sound/input on the emulated Amiga) proceeds.
2. Whether the target must use the 2 MB FastRAM (build then *requires* fast RAM) or stay within chip RAM (prompt default: no fast RAM). Default chosen: **use fast RAM if present, fall back to chip**, to be decided by measurement.
